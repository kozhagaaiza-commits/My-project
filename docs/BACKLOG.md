# Отложенные пункты (из ревью Дней 2–3)

Не блокируют работу, но их нужно закрыть до запуска. Каждый пункт привязан ко дню, где его удобнее сделать.

## Перед запуском в продакшн
- **Origin на превью Vercel.** `assertSameOrigin` сравнивает с `NEXT_PUBLIC_SITE_URL`; на превью-доменах `*.vercel.app` все POST дадут 403. Либо задать переменную под превью, либо допустить `https://$VERCEL_URL` при `VERCEL_ENV=preview`. (День 7, деплой)
- **Заголовки безопасности** (`next.config.ts`, Блок 5.10): X-Frame-Options, nosniff, HSTS и др. — не добавлены. (День 7)
- **Проверка на живой базе.** Все запросы к Supabase (каталог, брони, корзина) проверены только модульными тестами и фикстурами. Списки запросов PostgREST — в отчётах бэкенда Дней 2–3; проверить после открытия сети или на первом деплое.
- **`src/types/database.ts`** не сгенерирован (нужен доступ к проекту): `npx supabase gen types typescript --project-id $PROJECT_REF > src/types/database.ts`.

## Улучшения
- **`reserved_qty_map()` без фильтра** читает все активные брони при каждом просмотре карточки и validate; лимит PostgREST 1000 строк. Добавить опциональный `p_product_ids uuid[]` отдельной миграцией. (при росте нагрузки)
- **Лишний запрос validate** при открытии CartSheet после добавления: ответ add-flow не переиспользуется (`use-cart-validation`). Лимит 60/мин, на работу не влияет.
- **Фикстуры:** `price_asc/price_desc` сортируют по розничной цене и для ателье (на реальной БД сортировка по цене ателье, A26).
- **Чтение товара:** с `?vehicle=` `getProductBySlug` вызывается дважды (layout проверяет существование, page считает совместимость). Убрать можно только изменением контракта `catalog-queries.ts` (отдельная лёгкая функция существования).
- **Toast на mobile** (`bottom-center`) перекрывает sticky-панель карточки товара.
- **`cart-store.ts`** — 286 строк; при следующем изменении разбить на модули.

## Из ревью Дня 4 (не блокируют, платёжный контур)
- **Порядок в ветке `already_paid`** (`payments/process.ts`): строка платежа переводится в `succeeded` ДО `handleAlreadyPaid`. Если автовозврат упадёт на БД, сверка эту строку уже не увидит (ждёт повторную доставку webhook ЮKassa). Переставить: сначала `handleAlreadyPaid`, потом `updatePayment`. (До боевого запуска)
- **Общий потолок `/pay`** (`pay:<номер>`, 100/600 с) списывается до проверки токена: с десятка IP можно обнулить чужой потолок. Списывать после `verifyOrderAccess`. (До боевого запуска)
- **Платёж не в RUB** остаётся `succeeded` у неоплаченного заказа и перепроверяется сверкой каждый раз; при длинной `attention_reason` id обрезается и `admin_attention` может повторяться. Исключить такие платежи из `listSucceededPaymentsOfUnpaidOrders` отдельным признаком. (День 7, cron)
- **Админский возврат (День 6):** unique-индекс `uq_refunds_duplicate_payment` действует на любой `reason = 'Повторная оплата'`, в т. ч. введённый вручную — запретить это значение в Zod-схеме админского возврата или мапить 23505 в 409.
- **`maxDuration = 60`** нужно добавить и в маршрут cron (День 7); для `createRefund` в `duplicates.ts` желательно общий бюджет `deadlineMs`.
- **Уведомление об оплате** ставится «не больше одного раза»: при обрыве процесса между `mark_order_paid` и постановкой в очередь письмо теряется (заказ виден в админке). Для «хотя бы один раз» нужна дедупликация очереди.
- **Миграцию 20261003000000** (шаг 10 в `docs/APPLY_SQL.md`) применить до боевого запуска: без индекса защита от двойного возврата держится на `created_at` строки.
- **`ORDER_TOKEN_SECRET` не менять после запуска** (сломает все ссылки); в `.env.example`/чек-лист запуска добавить предупреждение.
- **Индекс для BR-18:** проверка неоплаченных заказов по email (`ilike`) не использует `idx_orders_email`; при росте — RPC `count_pending_orders_by_email`.
- **`getClientIp`:** первый адрес `x-forwarded-for` корректен на Vercel; за другим прокси (Cloudflare, nginx) нужен `x-vercel-forwarded-for`/`x-real-ip`.
